# Predictive Analytics for the German Energy Market

> **This project is a fork of [vsevolodnedora/energy_market_analysis](https://github.com/vsevolodnedora/energy_market_analysis) by [Vsevolod Nedora](https://github.com/vsevolodnedora).**
>
> All original domain knowledge -- curated weather station locations, physics-based feature engineering, spatial aggregation methods, the multi-step recursive forecasting architecture, and the automated pipeline design -- comes from the upstream project. See the upstream [README](https://github.com/vsevolodnedora/energy_market_analysis#readme), the [live demo](https://vsevolodnedora.github.io/energy_market_analysis/), and the author's [Medium articles](https://medium.com/@vsevolod.nedora) for the full project history, motivation, and detailed technical write-ups. This fork adapts the infrastructure for a specific downstream use case and is not affiliated with the original author.

## Overview

This project produces **weather-based forecasts of electricity generation and load** for the German market, broken down by TSO region. It is a companion to a separate energy_prices project that forecasts day-ahead electricity prices.

**The problem:** SMARD publishes TSO generation and load forecasts at ~18:00 CET, six hours *after* the 12:00 CET day-ahead auction. The price models need these as input features but cannot wait for the official numbers. This project produces equivalent forecasts from Open-Meteo weather data, which is available days in advance.

## How It Works

The forecasting framework follows the architecture designed in the [upstream project](https://github.com/vsevolodnedora/energy_market_analysis). The description below is adapted from the upstream README, modified only where this fork diverges.

### Data Collection

Automated daily data retrieval from public APIs, collected via GitHub Actions and appended to parquet datasets in `database/`:

- **[SMARD v2](https://smard.api.proxy.bund.dev/)**: Per-TSO generation and load actuals for each of the four German TSOs (50Hertz, Amprion, TenneT, TransnetBW) plus Luxembourg (Creos). Replaces the upstream's ENTSO-E dependency -- no API key required.
- **[SMARD](https://www.smard.de/home)**: Aggregated national energy data (generation by type, load, cross-border flows).
- **[Open-Meteo](https://open-meteo.com/)**: Weather data (wind speed, temperature, shortwave radiation, precipitation, etc.) for 30+ curated locations near actual generation assets -- major cities, wind farms, and solar parks. Open-Meteo provides separate APIs for historical data, past forecasts, and future forecasts; all three are combined into continuous time series for training and inference.
- **[EPEX SPOT](https://www.epexspot.com/en)**: Day-ahead and intraday auction prices, retrieved from files generated by the upstream author's [webscraper](https://github.com/vsevolodnedora/epex_de_collector).

### Feature Engineering

Each forecast target uses specialised physics-informed features (implemented in `data_modules/feature_eng.py`), as designed in the upstream project:

- **Wind generation** (offshore and onshore): Raw weather features (wind speed, direction, pressure) plus engineered features -- air density, wind shear profiles, wind power density (0.5 * rho * v^3), turbulence intensity, gust factor, cyclic wind direction encoding. Features are spatially aggregated across multiple wind farm locations using installed capacity weights or inverse distance weighting.
- **Solar generation**: Shortwave radiation, cloud cover, solar angle calculations, effective solar irradiance.
- **Load**: Temperature-based heating and cooling degree days, dew point, wind chill, humidex.

Feature selection and spatial aggregation method are treated as hyperparameters and optimised alongside model parameters during fine-tuning.

### Forecasting Models

The project uses **multi-step, recursive, single-target forecasting** -- each hourly timestep is forecast using the previous one, producing a 168-hour (7-day) horizon. This is the same approach as the upstream project.

**Base models:**
- LightGBM, XGBoost, ElasticNet -- each wrapped with [MAPIE](https://github.com/scikit-learn-contrib/MAPIE) for conformal prediction intervals.

**Ensemble models:**
- Stacking ensembles trained on out-of-sample predictions from base models (e.g., `ensemble[LightGBM](LightGBM, ElasticNet)`). As described in the upstream project, ensembles learn to overcome systematic errors in individual models.

**Multi-target models** (for energy mix):
- CatBoost, LightGBM, ElasticNet -- forecasting multiple generation sources simultaneously.

### Pipeline Automation

The pipeline follows the upstream's split between on-premises and cloud execution:

1. **Fine-tune** (Optuna) -- Computationally expensive hyperparameter search over model and dataset parameters. Run on-premises.
2. **Train** -- Train on the full dataset using the best parameters from fine-tuning. Run on-premises.
3. **Forecast** -- Inference using pre-trained models. Lightweight, runs daily in GitHub Actions.
4. **Publish** -- Process forecasts for the static webpage and deploy to GitHub Pages.

The workflow chain (`collect_data.yml` -> `update_forecasts.yml` -> `publish_forecasts.yml` -> `deploy.yml`) executes automatically on a daily schedule.

## Changes From Upstream

### Data source replacement

**Replaced ENTSO-E with SMARD v2.** The upstream repo requires an ENTSO-E API key, which was unavailable due to technical issues on the ENTSO-E side. This fork uses the freely accessible SMARD v2 API for per-TSO generation and load actuals, eliminating the ENTSO-E dependency entirely. A new collector module (`collect_data_smard_v2.py`) fetches data for each TSO with proper handling of missing data series (e.g., no offshore wind for inland TSOs, no lignite for TransnetBW).

### DE/LU bidding zone coverage

**Added Luxembourg (Creos TSO).** Germany and Luxembourg share a single electricity bidding zone. The upstream project covers only the four German TSOs. This fork adds:
- Creos TSO to the SMARD v2 collector (7 generation/load columns)
- Luxembourg weather locations (Luxembourg City, Bissen Solar Park, Hein Wind Farm)
- Per-TSO models for Luxembourg wind onshore, solar, and load
- A national `gen_load_diff` target (total generation minus total load across all 5 TSOs) that captures net cross-border exports, grid losses, and storage effects. At inference: `total_gen = load_forecast + gen_load_diff_forecast`, then `sonstige = total_gen - wind - solar`.

### Bug fixes

- **XGBoost float32 JSON serialisation** -- XGBoost 3.x returns float32 metrics that the standard JSON encoder cannot serialise. Added a `NumpyEncoder` to handle numpy types in all metadata writes.
- **XGBoost + MAPIE precision crash** -- XGBoost 3.x predicts float32 while MAPIE's `AbsoluteConformityScore` defaulted to `eps=1e-6` (below float32 precision). Fixed by setting `eps=1e-4`.
- **Non-destructive parquet column merging** -- The SMARD v2 collector's incremental update function was overwriting historical data when merging new columns. Fixed by using `combine_first` instead of direct assignment.
- **Stale exogenous forecast handling** -- Old forecast CSVs from previous runs could crash the pipeline when weather data was refreshed. Now drops all-NaN exogenous columns gracefully.

### Pipeline improvements

- **Region filter for training** -- Added an optional 6th CLI argument to `update_forecasts.py` to target specific TSO regions during fine-tuning and training, avoiding unnecessary re-processing of already-trained models.
- **NaN imputation for SMARD reporting gaps** -- Mean fill for known gaps in SMARD v2 data (e.g., `hydro_ampr` not reported before mid-2020).
- **Auto-fallback for new TSO weather data** -- The Open-Meteo update function now automatically falls back to a full initial download when encountering a new TSO directory.
- **Enabled CatBoost** in the energy mix pipeline (was commented out in upstream).

## Setup

### Prerequisites

- Python 3.11 (tested with 3.11.5)
- conda (recommended) or pip

### Installation

```bash
git clone <this-repo-url>
cd energy_market_analysis

conda create -n energy_market python=3.11
conda activate energy_market

pip install -r requirements.txt
```

No API keys required. All data sources (SMARD, Open-Meteo) are freely accessible.

### Key dependencies

- lightgbm 4.6, xgboost 3.2, catboost
- mapie 0.9.2 (not 1.x -- API break with `MapieRegressor`)
- optuna (hyperparameter tuning)
- open-meteo SDK, pandas, scikit-learn

## Usage

### 1. Update database

Collect weather and energy data from APIs:

```bash
python update_database.py DE update_smard_v2 hourly
python update_database.py all update_openmeteo_windfarms_offshore hourly
python update_database.py all update_openmeteo_windfarms_onshore hourly
python update_database.py all update_openmeteo_solarfarms hourly
python update_database.py all update_openmeteo_cities hourly
```

### 2. Fine-tune and train models

```bash
# Fine-tune hyperparameters (Optuna -- computationally expensive, run on-premises)
python update_forecasts.py DE wind_offshore LightGBM finetune hourly

# Train on full dataset with best parameters
python update_forecasts.py DE wind_offshore LightGBM train hourly

# Target a specific TSO region (optional 6th argument)
python update_forecasts.py DE solar LightGBM finetune hourly LU_CREOS

# Batch retraining
bash run_full_retraining.sh
```

### 3. Generate forecasts

```bash
# Lightweight inference using trained models (runs in GitHub Actions)
python update_forecasts.py DE all all forecast hourly
```

### 4. Publish

```bash
python publish_data.py DE all
```

### Argument reference

| Script | Argument | Values |
|--------|----------|--------|
| `update_database.py` | country | `DE`, `FR`, `all` |
| | task | `update_smard`, `update_smard_v2`, `update_openmeteo_windfarms_offshore`, `update_openmeteo_windfarms_onshore`, `update_openmeteo_solarfarms`, `update_openmeteo_cities`, `all` |
| | freq | `hourly`, `minutely_15` |
| `update_forecasts.py` | target | `wind_offshore`, `wind_onshore`, `solar`, `load`, `gen_load_diff`, `energy_mix`, `all` |
| | model | `LightGBM`, `XGBoost`, `ElasticNet`, `ensemble[...]`, `MultiTargetLGBM`, `MultiTargetElasticNet`, `all` |
| | mode | `finetune`, `train`, `forecast`, `plot`, `summarize`, `all` |
| | region | *(optional)* `DE_50HZ`, `DE_TENNET`, `DE_AMPRION`, `DE_TRANSNET`, `LU_CREOS`, `DE_LU` |

## Architecture

### Data flow

```
Open-Meteo API ──> database/{country}/openmeteo/   ──┐
SMARD v2 API   ──> database/{country}/smard_v2/    ──┤──> update_forecasts.py ──> output/{country}/forecasts/
SMARD API      ──> database/{country}/smard/        ──┤                                    │
EPEX files     ──> database/{country}/epexspot/     ──┘                          publish_data.py ──> deploy/data/
```

### Key modules

- **`data_collection_modules/`** -- API collectors and location metadata. `eu_locations.py` contains 30+ curated weather station coordinates near actual generation assets, TSO mappings, and installed capacity data.
- **`data_modules/`** -- Physics-informed feature engineering (`feature_eng.py`): wind power density, air density correction, wind shear profiles, solar angle calculations, heating/cooling degree days.
- **`forecasting_modules/`** -- ML pipeline with Optuna hyperparameter tuning, MAPIE prediction intervals, and ensemble stacking.

### Pipeline flow

1. `update_forecasts.py` creates task configs per target/TSO region
2. `interface.py` loads and cleans data, creates forecasting tasks
3. Tasks execute: **finetune** (Optuna) -> **train** (full dataset with CV) -> **forecast** (inference) -> **summarize** (metrics)
4. Fine-tuning and training run on-premises; forecasting runs daily in GitHub Actions

## Model Performance

Best model R² by target (5-fold rolling evaluation, 168h horizon):

| Target | Best model | R² range across TSOs |
|--------|-----------|---------------------|
| Load | LightGBM | 0.77 -- 0.94 |
| Solar | LightGBM | 0.32 -- 0.90 |
| Wind onshore | LightGBM / Ensemble | 0.45 -- 0.80 |
| Wind offshore | Ensemble | 0.51 -- 0.81 |
| Gen-load diff (DE/LU) | Ensemble[LGBM] | 0.74 (mean) |

Energy mix (conventional generation by fuel type) has poor performance (negative R² on gas, coal, lignite targets) due to missing economic features (fuel prices, CO2 prices, merit order). This is a known limitation also present in the upstream repo.
